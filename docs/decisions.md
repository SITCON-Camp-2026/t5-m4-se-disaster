# 需求取捨決策

> 這份文件目前是 Codex 產生的決策草稿，不是最終結論。請人類成員勾選、刪改或補充理由後，再當成 v1 方向。

## 我決定 v1 優先服務的使用者

請勾選一個主要對象，也可以補充原因。

- [ ] 回報者
- [x] 資訊整理者
- [ ] 行動者

原因：

我們選擇先服務「資訊整理者」，因為目前 Phase 0 原始資訊最大的問題不是缺少行動入口，而是資料還沒有被安全理解。許多內容來自轉述、群組、截圖或不完整描述，若直接面向行動者，畫面很容易把「候選整理」誤看成「可以出發」；若直接面向回報者，又會太早進入輸入流程，反而沒有處理既有資料中的不確定性。

資訊整理者最需要做的事，是保留原文、標出缺口、分清楚查核狀態與整理進度，並把不能直接變成任務的原因說清楚。這也最符合 v1 的學習目標：不是讓系統決定什麼是真的，而是讓下一位協作者知道哪些地方仍需要人工確認。

Subagent 補充：三個 persona 都指出「已整理」「優先」「候選」可能讓人誤以為資料更可信或更可行動，因此 v1 若要繼續服務資訊整理者，必須先把這些狀態文字講清楚。

## 這個使用者最想完成什麼

- 把混亂原始資訊整理到下一位協作者能理解。
- 分清楚原文、AI 推測、人類修正、查核狀態與整理進度。
- 找出缺少哪些資訊，以及哪些內容需要人工確認。

## 這個使用者最怕什麼錯誤

- 把模糊、轉述或未查核資訊包裝成已確認事實。
- 把整理草稿、最新排序或優先標記誤當成可信度。
- 讓下一位協作者不知道哪些內容來自原文，哪些只是推測。
- 看到「已整理」「任務候選」後，以為有人已經查過或可以派人行動。

## 我今天暫時不處理的需求

- 暫時不做真實回報表單或真實送出流程。
- 暫時不做給行動者直接接任務的介面。
- 暫時不做地圖、外部 API、後端、資料庫或 runtime LLM。

## 我不採用的 AI 建議

- AI 建議：把 persona 回饋直接轉成 v1 功能清單。
  - 不採用原因：Release 01 目標是需求分析與取捨，不是立刻實作；直接列功能會掩蓋 persona 之間的衝突。
- AI 建議：把「任務候選」做得更醒目，方便行動者快速找到可做的事。
  - 不採用原因：目前資料仍來自 Phase 0 原始資訊，未確認內容不能被暗示為可行動任務。

## 必須保留人工確認的判斷

- 是否已確認、是否可以行動、是否能派工。
- 轉述者是否為當事人或現場窗口。
- 模糊地點、時間、需求數量、資源狀態與安全條件。
- AI 推測是否有原文依據。

## 今天明確不做什麼

- 不修改 `src/`，不進行前端實作。
- 不新增真實資料、地圖、地址、電話、人物或外部查詢。
- 不把 release pack 或 persona 回饋改寫成正式答案。
- 不讓 AI 替小隊做最後決策。

## 我仍不確定的地方

- 人類成員是否同意 v1 優先服務資訊整理者。
- 首頁的「最新」「讚」「優先」是否應在 v1 改名，避免被誤解成可信度。
- 「候選整理」這個詞是否足夠清楚，還是仍會讓使用者誤以為資料已被確認。
- 「已整理的」頁籤是否應改成更明確的草稿語氣，避免被看成完成品。
